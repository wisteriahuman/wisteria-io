# 開発者ストーリー

開発する人（[ペルソナ](./personas.md#開発する人)）が何を達成したいかを書く。アーキテクチャ・ディレクトリ構成・技術選定・開発体験の設計の入力にする。

ステータス: 確定（2026-10-15）。各ストーリーの「状態」は、達成したら根拠を添えて更新する。

## 考え方

ユーザーストーリーが「製品を使う人」の目的を書くのに対し、開発者ストーリーは「製品を変更する人」の目的を書く。

```
開発者ペルソナ → 開発者ストーリー → 開発者ジャーニー → 受け入れ条件
（誰が開発するか）（何を達成したいか）（コード上でどう達成するか）（何をもって良い体験とするか）
```

- 「どの構成が正しいか」という一般論の議論は、「このペルソナがこのストーリーを遂行するとき、どちらが良い体験になるか」に置き換えると答えが出る
- 「この変更が来たとき影響がどこまで広がるか」を見るチェンジシナリオは、受け入れ条件として吸収する
- 開発者ジャーニーは、実装が進んで実際の手順が見えてから書く

## 書き方

```
### DS-XX: [短い名前]
- ペルソナ:
- ストーリー: 〈ペルソナ〉として、〈したいこと〉。〈なぜなら〉
- 受け入れ条件:
- 段階:
- 状態: 達成 | 一部達成 | 未着手（根拠: PR・検査・ファイル）
```

## 自分

### DS-01: 記事を push だけで公開する
- ペルソナ: 自分
- ストーリー: 自分として、思いついた記事を Neovim で書き、push するだけで公開したい。細切れの時間でも発信を続けるため
- 受け入れ条件:
  - 記事の追加は Markdown ファイル1つで完結する
  - OGP 画像は自動で生成される
  - push から本番反映まで10分以内
- 段階: ②
- 状態: 一部達成。Markdown 1ファイルで完結し、OGP は自動で作られる（src/pages/og/）。push から本番までの時間はまだ測っていない

### DS-02: 実績を1か所直せば全体に反映される
- ペルソナ: 自分
- ストーリー: 自分として、実績が増えたとき、1か所を直すだけで最初の画面・経歴・OGP に反映したい。直し忘れで情報が食い違わないようにするため
- 受け入れ条件:
  - 実績のデータが1か所にまとまっている
  - 最初の画面・経歴・OGP がそのデータから作られる
- 段階: ①
- 状態: 達成。src/data/ から最初の画面・経歴・OGP を作り、pnpm check で食い違いを検出する（scripts/check-dist.mjs）

### DS-03: 間があいても判断の経緯を思い出せる
- ペルソナ: 自分
- ストーリー: 自分として、数週間ぶりに触っても、なぜ今の構成なのかをすぐ思い出したい。過去の判断を誤って崩さないため
- 受け入れ条件:
  - 技術選定・設計の判断がすべて ADR にある
  - `docs/README.md` から目的・判断・設計に辿れる
- 段階: ①
- 状態: 達成。判断は ADR-001〜017 にあり、docs/README.md から辿れる

### DS-04: インフラの変更をコードの差分として扱う
- ペルソナ: 自分
- ストーリー: 自分として、インフラの変更をコードの差分として確認し、問題があれば戻したい。手作業の変更で構成が分からなくなるのを防ぐため
- 受け入れ条件:
  - インフラのリソースはすべて Terraform・マニフェストで管理されている
  - 手作業のデプロイ・インフラ変更が0回
- 段階: ②
- 状態: 未着手（段階②-c）

### DS-05: どの機械でも開発環境を再現できる
- ペルソナ: 自分
- ストーリー: 自分として、Mac でも Linux でも、同じ手順で開発環境を用意したい。機械を選ばずに作業するため
- 受け入れ条件:
  - `guides/setup.md` の手順だけで開発サーバーが起動する
  - ツールのバージョンが固定されている
- 段階: ②
- 状態: 達成。.node-version と packageManager で固定し、手順は guides/setup.md（ADR-012）

### DS-09: 自宅が止まってもサイトが見られ続ける
- ペルソナ: 自分
- ストーリー: 自分として、自宅の機械が止まっても、何もしないうちにサイトが見られ続けてほしい。旅行中や就活中に止まっても、見る人を待たせないため
- 受け入れ条件:
  - 自宅が止まると、予備（AWS）に自動で切り替わる
  - 月間稼働率 99.9%
- 段階: ②
- 状態: 未着手（段階②-c）

### DS-10: PR を開けば本番の前に見た目を確かめられる
- ペルソナ: 自分
- ストーリー: 自分として、PR を開いたら、本番に出す前にその見た目を確かめたい。見た目の崩れを本番で初めて知ることがないようにするため
- 受け入れ条件:
  - このリポジトリから出た PR は、verify の後に staging に出る
  - staging は検索に載らない
- 段階: ②
- 状態: 達成。このリポジトリの PR は verify の後に staging に出て、noindex が付く（ADR-015、PR #9）

### DS-11: 構成図を手で描かずに済む
- ペルソナ: 自分
- ストーリー: 自分として、インフラの構成図を手で描かずに、実際の構成から作りたい。図と実物が食い違わないようにするため
- 受け入れ条件:
  - `/infra` の構成図が、マニフェスト・Terraform から生成される
- 段階: ②
- 状態: 未着手（段階②-d）

## AI エージェント

### DS-06: 既存のパターンを見つけて正しい場所に追加する
- ペルソナ: AI エージェント
- ストーリー: AI エージェントとして、新しいセクションやページを追加するとき、既存のパターンを見つけて迷わず正しい場所に追加したい。推測で構成を崩さないため
- 受け入れ条件:
  - CLAUDE.md から docs への導線がある
  - コンポーネントとデータの置き場所に一貫した規則があり、`rules/` に書かれている
- 段階: ②
- 状態: 達成。置き場所の規則は rules/code-structure.md

### DS-07: 変更をコマンド1つで検証する
- ペルソナ: AI エージェント
- ストーリー: AI エージェントとして、変更が要件を満たしたかをコマンド1つで確かめたい。人の確認を待たずに誤りに気づくため
- 受け入れ条件:
  - ビルド・型検査・リント・Lighthouse の確認が1つのコマンドで走る
  - CI でも同じコマンドが走る
- 段階: ②
- 状態: 達成。pnpm verify が型検査・リント・ビルド・ビルド結果の検査・単体の検査（pnpm test）・Lighthouse を走らせ、CI も同じコマンドを使う（ADR-010・ADR-011）

### DS-08: 判断を伴う変更で ADR と矛盾しない
- ペルソナ: AI エージェント
- ストーリー: AI エージェントとして、技術選定を伴う変更をするとき、既存の ADR と矛盾しないかを確かめ、新しい ADR の下書きを作りたい。判断の記録を途切れさせないため
- 受け入れ条件:
  - ADR の一覧とステータスが `adr/` から分かる
  - 判断を伴う変更には ADR の追加・更新が伴うことが `rules/` に書かれている
- 段階: ②
- 状態: 達成。一覧は adr/README.md、ADR を伴わせる規則は rules/docs.md

### DS-12: 部品を足しても、判断へのリンクを手で書かずに済む
- ペルソナ: AI エージェント
- ストーリー: AI エージェントとして、セクションや部品を足したとき、それを決めた PR と ADR へのリンクを手で書かずに済ませたい。リンクの書き漏れで「この部分の作り」が嘘にならないようにするため
- 受け入れ条件:
  - PR は git の履歴から自動で拾われる
  - ADR とファイルの対応は1か所に書かれ、抜けを `pnpm check` で検出できる
- 段階: ②
- 状態: 達成（PR #14。対応表は `src/data/build-notes.ts`、抜けは `pnpm test` と `pnpm check` が検出する）
