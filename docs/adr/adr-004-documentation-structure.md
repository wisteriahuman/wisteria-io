# ADR-004: ドキュメントを用途別に分け、テンプレートで書く

- ステータス: 採用
- 日付: 2026-10-14

## 背景・課題 (Background/Problem)
- 要件・判断・設計を会話の中だけで決めると、後から自分も AI エージェントも経緯を辿れない
- 面接官がリポジトリを見たとき、判断の根拠がどこにあるか分かる必要がある
- 書き方が文書ごとにばらつくと、読む側の負担が増える

## 決定事項 (Decision)
- `docs/` を用途別に分ける: `requirements/`・`adr/`・`design/`・`guides/`・`rules/`
- 各ディレクトリに `TEMPLATE.md` を置き、新規作成時はコピーして使う
- 意思決定はすべて ADR に残す。ADR は `adr-XXX-<内容>.md` の連番で命名し、ステータスと日付を持つ
- 要件は、目的と指標・ペルソナ・ユーザーストーリー・開発者ストーリーに分ける

### 理由 (Reasons)
- Go College（2026年9月）の個人開発で同じ構成を運用し、設計意図の共有に効いた
- 用途ごとに置き場所が決まっていれば、AI エージェントも迷わず読み書きできる（→ DS-06, DS-08）
- テンプレートがあれば、検討した選択肢やトレードオフの書き漏れを防げる

### 受け入れるトレードオフ (Accepted Trade-offs)
- 小さな判断でも ADR を書く手間がかかる
- 個人のサイトとしてはドキュメントが重い。ただしこのサイトはドキュメントの質そのものも見せる対象とする

## 検討した別の選択肢 (Alternatives Considered)
- **README に全部書く**: 手軽だが、判断の履歴が残らず、量が増えると読めなくなる
- **外部ツール（Touchstone 等）に置く**: 構造化はできるが、面接官がリポジトリから見られない

## 参考 (References)
- [Architecture Decision Records](https://adr.github.io/)

## 議論 (Discussion)
- Go College の構成のうち、`api/` は静的サイトのため作らない
- ADR テンプレートには、提案中の判断を区別するためステータスと日付を足した
- design テンプレートには、ui-grill で詰める項目と ui-ux-pro-max の参照欄を足した
- 2026-10-15: Superpowers が書く仕様書と実装計画は `superpowers/specs/`・`superpowers/plans/` に置く。design は「何を作るか」、superpowers は「どのファイルにどう作るか」と分ける。テンプレートは Superpowers の形式に従うため置かない
- 2026-10-15: アイデアソンの記録は `ideathon/` に置く。案の全部と採否の理由を残し、採った案は ui-grill を経て design に入る。形式は `ideathon` スキルの記録に従うため、テンプレートは置かない
